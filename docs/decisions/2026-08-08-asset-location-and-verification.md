## 1. 素材の置き場所

### 問題

[技術スタックの決定](2026-08-07-tech-stack-and-boundary.md)は「1リポジトリに全作品を同居」と決めたが、
これは**コードの置き場所**についての決定であり、**バイナリ素材**を扱っていなかった。

git はバイナリの差分を持てないため、素材を1回差し替えるたびに履歴が丸ごと太る。
現在のダミー素材が 652KB で済んでいるのは中身が空だからで、実素材は1作品で
数百MB〜GB規模になり得る。加えて、購入素材は公開リポジトリに置けない。

### 素材の出所と、そこから来る制約

| 出所 | 制約 |
|---|---|
| 購入・ストック素材 | 再配布禁止。公開リポジトリには物理的に置けない |
| 生成AI | 差し替えが頻繁。履歴が単調増加する |
| 自作 | 制作中の差し替えが頻繁。同上 |
| フリー素材 | 容量のみ |

**出所も公開範囲も未定**という前提で決めた。どの出所でも共通する要求は
「素材をリポジトリの外に出せること」だけで、それ以外に共通項はない。

### 決定: 素材ディレクトリを作品ごとに差し替え可能にする

`novels/<作品ID>/novel.config.json` を**任意で**置ける。既定は `<作品ディレクトリ>/public`。

```json
{ "assetsDir": "../../../wn-assets/kieta-ippen" }
```

- 相対パスは**作品ディレクトリ基準**で解決する。絶対パスも使える
- **設定ファイルは任意。** 必須にすると「作品を増やすコストはディレクトリ1つ」
  という前記決定の前提が崩れる
- 明示した `assetsDir` が存在しなければビルドエラー（設定ミスなので落とす）。
  既定値 `public` の不在は許す（本文だけの作品が成立するため）

結合点は2つしかなく、どちらも `vite.config.ts` の `root` から導出されていた。

| 場所 | 変更 |
|---|---|
| `tools/wn-compile/index.ts` | `wnCompile({ root })` → `wnCompile({ assetsDir })` |
| Vite の `publicDir` | 既定値 `<root>/public` → `assetsDir` を明示 |

`runtime.resolveAsset()` はページ URL 基準の相対解決なので、素材がビルド時に
どこから来たかを知らない。実行時のコードは1行も変わらない。

### これは問題を解いていない。先送りを安全にしている

実素材が来た日に、改めて Git LFS か取得マニフェスト方式かを決める必要は残る。
それでよいと判断した根拠は、その日まで待てば「取得元」「公開範囲」「実容量」という
3つの未知が既知になっていること。今それらを仮定して選ぶと、仮定が外れたときに
書いたコードが捨てになる。

**却下した案**

| 案 | 却下理由 |
|---|---|
| 取得マニフェスト方式（`npm run fetch:assets`） | 取得元（S3・別リポジトリ・NAS）がまだ存在しない。決まっていない前提の上に実装することになる |
| Git LFS を今から導入 | LFS 対応ホスティングを前提にするが、公開範囲が未定。再配布禁止素材の問題も解決しない |
| ダミー素材を `.gitignore` して生成に切り替える | 652KB でライセンス上の問題もない。外すと clone 直後に `npm test` と `npm run dev` が落ちる。**外に出す原則は実素材に適用するもので、ダミーには利がない** |

### 素材の秘匿はエンジンの責務にできない

静的サイトである以上、配信した素材は必ず取得可能で、これを防ぐ方法はない。
したがって「取り出されては困る素材」はこのエンジンに載せられない。

裏を返すと、この設定が守るのは**リポジトリに原本を置かないこと**だけであり、
難読化・暗号化は設計から外れる。

なお「再配布禁止素材は使えない」という結論にはならない。ライセンスが禁じる再配布とは
素材を素材として渡す行為であり、完成した作品に組み込んで配信することは購入の目的そのもの。
完成品から素材が技術的に取り出せることは、あらゆる媒体で当たり前に起きている。

**実際に注意が要るのは別のところ。**

- **フォント** — Web 配信は別ライセンス（Webフォント版）が必要なことが多い。
  現在 `style.css` が `system-ui` を使っているのはこの問題を回避している
- **音源** — 「楽曲として取り出せる形での配信」を制限するライセンスがある
- ライセンスの範囲（Web 配信可か、商用可か）は素材ごとに違う

素材ごとに **Web 配信が許諾範囲に入っているかを買う前に確認する**、という運用で扱う。
エンジンの設計では解けない。

## 2. 演出中のクリック

engine-spec は「文字送り中のクリック」を決めていたが、`@wait 600` や
`@bg fade:800` の最中にクリックしたときの挙動を定義していなかった。

**現在の待ちだけを打ち切る。** 連打すれば連続でスキップされる。

文字送りのクリックが「内容を飛ばす」ではなく「早く見せろ」を意味する以上、
演出だけ別の意味になるのは一貫しない。実装は Task 11（`@wait`）で行う。

**却下した案** — 無視のまま。書き手が意図した間を読者が飛ばせない代わりに、
クリックが効かない瞬間が生まれる。読者から見ると操作不能に見える。

## 3. ブラウザでの確認は `tests/e2e/` に残す

コアが React にも DOM にも依存しないため Vitest で大半は検証できるが、
**背景・立ち絵・音声・ページ分割は DOM でしか確認できない。**
フェーズ4以降はこれらが主題になる。

Playwright を devDependency に入れ、`tests/e2e/` に置く（`npm run test:e2e`）。

**DOM の値を assert するテストだけを置き、スクリーンショット比較は採らない。**
壊れやすく、維持コストが実利を上回るため。

これに伴い、`.wn-stage` に `data-phase` 属性を出すようにした。
E2E が進行を決定的に待つための手掛かりであり、Task 9 以降の CSS フックでもある。
これが無いと、文字送りの途中を掴んでテストが不安定になる。

**弱点** — 計画は E2E を勘定に入れていない。一人開発でここまでやるのは過剰という
判断も成立する。それでも入れたのは、フェーズ4の主題が DOM 側にあるため。

## 4. `view` の配列の不変性はテストで固定する

`Runtime.emit()` は `EngineState` の3層をそれぞれ浅くコピーして参照を差し替えるが、
`sprites` や `backlog` を**配列のまま `push` すると参照が変わらず、React が再描画しない。**

現状これを守っているのは `emit()` のコメントだけで、ESLint では落とせない。

**Task 10（立ち絵）と Task 14（バックログ）で、配列の参照が変わることを assert する。**

**却下した案** — dev ビルドで `Object.freeze`。確実だが、本番と dev で振る舞いが分かれる。

## この決定が後段に与える制約

| 制約 | 影響先 |
|---|---|
| 素材ディレクトリは `resolveAssetsDir()` が唯一の解決点 | 素材を扱うツールを増やすときはここを通す |
| 実素材はリポジトリに置かない | 実素材の調達時に、改めて LFS か取得方式かを決める |
| 演出中のクリックは現在の待ちを打ち切る | Task 11。以後の演出命令もこの規則に従う |
| DOM の値で検証できる状態を保つ | 新しい演出は E2E から観測できる形で出す（`data-phase` など） |
| 配列は置き換える | 新しい配列状態を `view` / `snapshot` に足すたびにテストを1つ足す |
