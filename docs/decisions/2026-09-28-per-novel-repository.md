# 作品ごとに独立したリポジトリを作る

- 決定日: 2026-09-28
- 対象: リポジトリ構成、作品の作り方と配信、`README.md`、`docs/architecture.md`

> これは決定時点のスナップショットである。現在の確定構成は
> `docs/architecture.md` にある。

## 決めたこと

1. **作品は、作業を始めるときに独立したリポジトリを作り、そこで作る。**
   新しいリポジトリは、このエンジンリポジトリをエンジンごとほぼコピーして作る。
   エンジンを依存パッケージとして参照するのではなく、コピーを持つ。
2. **作品リポジトリでは、エンジンのコードも自由に変更してよい。**
   その作品に固有の制御は、作品リポジトリの中だけでカスタマイズしてよい。
3. **作品が完成したら、汎用的な改善をこのエンジンリポジトリに反映する。**
   作品固有のカスタマイズは反映しない。何が汎用的かは反映するときに判断する。
4. **このエンジンリポジトリは、エンジンの正本と動作確認用の作品だけを持つ。**
   `novels/kieta-ippen/` は全命令が登場する台本で、E2E が依存しているため残す。
5. **作品は ankardo に配信する。** 配信先は `ankardo.com/play/<作品ID>/` を想定する。
6. **エンジンが作り込めたと判断するまでは、このリポジトリの `novels/` で書いてよい。**
   ただしコミットしない（`.gitignore` で `novels/kieta-ippen/` 以外を外す）。
   作品リポジトリを作るのは、エンジンをある程度作り上げたと判断した時点。

## 2026-08-07 の決定を覆した

[技術スタックと、エンジン・作品の境界](2026-08-07-tech-stack-and-boundary.md)は
「1リポジトリに全作品を同居させ、ビルド単位を作品ごとに分ける」だった。
このとき「作品ごとに別リポジトリ（submodule 含む）」と
「エンジンを npm publish、作品は別リポジトリ」は、
**エンジン改修時に全リポジトリを往復することになる**という理由で却下している。

この却下理由は、作品リポジトリが**エンジンを依存として参照する**前提に立っていた。
その前提では、作品を書く途中で命令を1つ足すたびに、エンジンを直す → バージョンを切る →
作品側で上げる、という往復が要る。このエンジンは「台本に出てきた命令だけを足す」方針なので、
エンジンが最もよく変わるのは作品を書いている最中であり、往復のコストは重い。

今回の形は**コピーを持つ**ので、この往復が起きない。作品を書きながら、
作品リポジトリの中のエンジンをそのまま直せる。エンジンリポジトリへの反映は完成時に1回だけ。

同居をやめて得るもの。

| 得るもの | 理由 |
|---|---|
| 公開した作品が後のエンジン変更で壊れない | 同居では `build:all` で全作品が追従する。裏を返すと、公開済み作品の挙動が後から変わる。セーブはシーン入口からのリプレイで復元するので、リプレイの処理が変わると読者の手元のセーブが別の画面に復元されうる |
| 作品固有の制御を入れられる | エンジンリポジトリを汚さずに済む。汎用かどうかの判断を完成時まで先送りできる |
| 作品ごとに公開・非公開を選べる | 台本はネタバレそのもの。同居ではリポジトリの公開範囲が全作品で共通になる |
| ankardo への載せ方を他のゲームと揃えられる | character-tactics は独自のリポジトリに `wrangler.toml` を持ち、`ankardo.com/play/character-tactics/*` のルートで配信している |

同居をやめて失うもの。

| 失うもの | 対処 |
|---|---|
| エンジンの改善が既存の作品に自動で届かない | 意図した性質（上の表の1行目の裏返し）。必要な修正は作品リポジトリへ手で持っていく |
| 完成時の反映を忘れうる | 作品リポジトリを作った時点で、反映の作業を Issue などに立てておく |
| 作品を並行して作ると、エンジンの変更が作品リポジトリ間で食い違う | 想定しているのは1作品ずつ順に作る進め方。並行するようになったら見直す |

**古い決定記録は書き換えていない。** それが記録としての価値だから。

## 採らなかったもの

| 案 | 却下理由 |
|---|---|
| 同居を続ける | 上の「得るもの」の表をすべて失う。特に、公開済み作品がエンジン変更で壊れうる点は、作品が増えるほど重くなる |
| このリポジトリで書き、完成してから独立したリポジトリに移す | エンジンを外から使える形（`@engine` エイリアス・Vite プラグイン・`NOVEL` 環境変数の外部化）に整える作業が要る。コピーならこの作業は不要。書いている最中に作品固有の制御を入れる場所も無い |
| 作品リポジトリがエンジンを依存として参照する（npm の git 依存・submodule） | 2026-08-07 の却下理由がそのまま当てはまる。命令を足すたびにリポジトリを往復する |

## 決めていないこと

- **コピーの手順。** GitHub のテンプレートリポジトリにするか、手でコピーするか。
  コピーから外すもの（`novels/kieta-ippen/`、`docs/` の履歴、`novel-to-wn` スキルの扱い）も含めて、
  最初の作品リポジトリを作るときに決める
- **ankardo への配信の設定。** character-tactics と同じく作品リポジトリに `wrangler.toml` を置く想定だが、
  未確定。`base: './'` は末尾スラッシュなしの URL（`/play/<作品ID>`）で素材の参照が壊れるので、
  ルートとリダイレクトの扱いを最初に確認する
- **実素材の管理。** リポジトリに置かない原則は変わらない。
  LFS か取得方式かは、2026-08-08 の決定どおり実素材を調達するときに決める
- **反映の手順。** 作品リポジトリの差分から、汎用的な改善をどう取り出してエンジンリポジトリに入れるか
