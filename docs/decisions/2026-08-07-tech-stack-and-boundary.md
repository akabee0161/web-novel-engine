## 1. エンジンと作品の境界

### 前提となった2つの回答

| 問い | 回答 |
|---|---|
| 読者から見た公開の形 | 独立公開だが同一オリジン（`domain.com/novelA/`） |
| エンジン改修時の既公開作品 | 全作品を再ビルドして追従 |

この2つにより、README が挙げていた3つの形のうち2つが消えた。
「ライブラリとして配布」は、バージョンを配る相手が存在しないため目的を失う。
「作品選択画面を持つ単一アプリ」は、README が「今は決めない」とした画面を構成の前提にしてしまう。

### 決定: 1リポジトリ、ビルド単位は作品ごと

```
web-novel-engine/
├── vite.config.ts
├── src/engine/
│   ├── index.ts          ← 作品が触ってよい唯一の入口
│   ├── core/             ← React 非依存
│   └── ui/               ← React
├── tools/wn-compile/     ← 台本コンパイラ
└── novels/
    ├── novelA/
    │   ├── index.html
    │   ├── main.ts
    │   ├── script.wn
    │   └── public/{bg,bgm,se,chara}/
    └── novelB/
```

**作品を1つ増やすコストは「`novels/` にディレクトリを1つ足す」だけ。**
設定ファイルは増えない。

```ts
// vite.config.ts（骨子）
export default defineConfig(() => {
  const novel = process.env.NOVEL
  return {
    root: `novels/${novel}`,
    base: './',
    build: { outDir: `../../dist/${novel}`, emptyOutDir: true },
    resolve: { alias: { '@engine': resolve('src/engine/index.ts') } },
    plugins: [react(), wnCompile()],
  }
})
```

```json
"scripts": {
  "dev":       "vite",
  "build":     "vite build",
  "build:all": "for d in novels/*/; do NOVEL=$(basename $d) vite build; done"
}
```

### デプロイ

作品Bだけ直したとき。

```
NOVEL=novelB npm run build
rsync -a --delete dist/novelB/ server:/var/www/html/novelB/
```

作品Aには一切触れない。エンジンを改修したときは `npm run build:all` で全作品が追従する。

`base: './'` により `dist/novelB/` は**配置場所に依存しない自己完結した成果物**になり、
`domain.com/novelB/` でも別ドメインでも動く。ルーティングを持たないため、
ホスティング側の SPA fallback や rewrite 設定は不要。

**注意点** — `base: './'` は相対パス解決なので、末尾スラッシュなしの URL
（`domain.com/novelB`）で index.html が配信されると資産の参照が壊れる。
デプロイ先を決めたら自動リダイレクトの有無を最初に確認する。

### 素材のパス解決

素材は作品ごとの `public/` に置き、エンジンが**現在のページ URL 基準の相対パス**として解決する。

```ts
new URL(`bg/${name}.webp`, document.baseURI)
```

台本は `@bg rain_street` と書くだけでよく、デプロイ先のパスはエンジンが吸収する。

### 作品ID

**作品側が `boot()` に明示的に渡す。**

```ts
import { boot } from '@engine'
import script from './script.wn'

boot({ mount: document.getElementById('app')!, script, novelId: 'novelA' })
```

ディレクトリ名から自動で拾わない。ディレクトリをリネームした瞬間に
ストレージキー `wn:<作品ID>:save:1` が変わり、読者のセーブが消えるため。

### 境界の強制

ESLint の `no-restricted-imports` で機械的に落とす。

1. エンジン → `novels/` への import を禁止
2. 作品 → `@engine` 以外の `src/engine/**` への import を禁止
3. `core/` → `ui/` への import を禁止
4. エンジン → `tools/` への import を禁止（型の依存は tools → engine の一方向）

### 却下した案

| 案 | 却下理由 |
|---|---|
| 共有チャンク方式（1回のビルドで全作品を出す） | デプロイ単位が `dist/` 全体になる。10作品あるとき1作品の修正で全体を上げ直すことになる。共有できるエンジンJSは数十KBで、素材が数MB〜数十MBあることを考えれば独立性のほうが桁違いに価値が高い |
| pnpm workspace で作品ごとにパッケージ化 | 境界がパッケージ境界として物理的に強制される利点はあるが、作品ごとに `package.json` と `vite.config.ts` が要る。一人開発なら ESLint で足りる |
| エンジンを npm publish、作品は別リポジトリ | エンジン改修時に全リポジトリを往復することになり、「全作品を再ビルドして追従」と正面から衝突する |
| 作品ごとに別リポジトリ（submodule 含む） | 同上。独立した履歴・権限・CI が買えるが、想定利用者が自分ひとりでは効かない |

将来 `novelA.example.com` と `novelB.example.net` のように別ホストへ分けたくなった場合も、
`dist/novelA/` が自己完結しているため構成変更なしで対応できる。
リポジトリ分割が本当に必要になったら、`novels/novelA/` を新リポジトリへ移し
`src/engine/` を submodule か npm 依存に置き換えればよい。

## 2. 技術スタック

### Vite + React + TypeScript

React を選ぶのは書き手が慣れているためであり、設定画面・セーブスロット・バックログといった
UI を宣言的に書けることによる。

**Next.js は却下した。** 提供する機能のうち使うのは「React をビルドして静的ファイルを出す」
1点だけで、SSR / RSC / ファイルベースルーティング / データフェッチ / next-image /
メタデータのいずれもこのエンジンでは使い道がない。

| 具体的な不利 | 内容 |
|---|---|
| 台本コンパイラの実装先 | Vite なら `transform` フックに数十行。Next は webpack/turbopack の loader を書くことになる |
| `'use client'` | エンジンは全てクライアント専用であり、境界を切る作業が全ファイルに発生して得るものがない |
| 構成の向き | Next は「1つのアプリに複数ルートを集約する」思想で、「独立公開」と決めた方向と逆に引っ張る |
| 起動と HMR | 文字送りやフェードの調整は反復回数が多く、体感差が積み上がる |

Next.js が正当化されるのは、セーブのクラウド同期や認証などサーバ側の処理が要る場合だが、
これは現在の仕様（保存先は端末ローカル、サーバなし）と矛盾する。

### 描画は DOM + CSS

| 命令 | 実装 |
|---|---|
| `@bg name fade:600` | 背景を2枚重ねて `opacity` を transition |
| `@show` / `@hide` | `<img>` の絶対配置。位置は `left`、表情は `src` 差し替え |
| `@flashback on` | ステージ全体に `filter` とオーバーレイを transition |
| 文字送り | 文字列の slice |

**Canvas / WebGL は使わない。** 必要になるのはピクセル単位のトランジション
（ルール画像によるワイプ、ディゾルブ）、パーティクル、シェーダ演出で、
`drafts/sample-short.wn` にこれらは1つも出てこない（README 目標1）。

副次的な利点として、自動ページ送りに必要なテキスト測定を Range API で
ブラウザに任せられる。Canvas なら `measureText` で自前計算になる。

将来ピクセル演出が必要になった場合、影響は `ui/Stage.tsx` に閉じる。
今その差し替えのための抽象は用意しない。

### 画面のスケーリング

基準解像度 **1280×720（16:9）** のステージをビューポートにフィットさせ、レターボックスする。
内部の寸法は `container-type: size` ＋ `cqw` 単位で表現する。
`transform: scale()` による一括拡縮だと、テキストがスケール後のラスタライズになり大画面で眠くなる。

**モバイルの縦持ちは未確定として残す。** engine-spec に規定がなく、実際に読まないと決まらない。

## 3. コアと描画層の分離

不変条件1（状態はスナップショット可能な1箇所に集約）と2（リプレイは決定論的）を、
規律ではなく構造で守る。

```
src/engine/
├── core/          React を一切 import しない素の TypeScript
│   ├── state.ts / runtime.ts / save.ts / read.ts
│   ├── backlog.ts / audio.ts / storage.ts / script.ts
└── ui/            React。core を購読して描くだけ
```

### 状態の3層

```ts
type EngineState = {
  snapshot: {                    // シーン境界で持ち越され、セーブに入る
    bg: string | null
    bgm: string | null
    sprites: Sprite[]
    speed: 'slow' | 'normal'
    flashback: boolean
    vars: Record<string, unknown>
  }
  progress: { scene: string; index: number; pc: number }
  view: {                        // 画面の一時状態。セーブに入らない
    phase: 'performing' | 'typing' | 'waiting'
    currentText: { speaker: string | null; body: string } | null
    visibleChars: number
    page: { current: number; total: number }
    fadeMs: number
    backlog: BacklogEntry[]
  }
}
```

セーブは `structuredClone(state.snapshot)` の一行になる。

**これが解いているのは列挙の重複である。** 3層に分けない場合、状態の定義とは別に
「セーブに入れるフィールドのリスト」がコード上に現れ、それが新命令追加時に
更新し忘れる場所になる。不変条件4が警告しているのは実質これであり、
3層なら列挙が消えるのでズレようがない。

ただし**型が保証するのは「忘れる」ことの防止だけで、「間違える」ことは防がない。**
新命令の状態を `snapshot` ではなく `view` に置いてもコンパイルは通る。
どの層に属するかの判断は依然として人間の仕事であり、不変条件4の本文は有効なまま残る。

`progress.pc` は `steps` 配列上の位置で、セーブには入らずリプレイで再計算される。

### React との接続

```ts
const state = useSyncExternalStore(runtime.subscribe, runtime.getState)
```

**`useState` にエンジンの状態を置くコンポーネントを作らない**ことが唯一の規律。
設定画面の一時的な入力値などは別だが、`snapshot` に属するものは必ずコア側にある。

音声はコアの `audio.ts` が Web Audio を直接持ち、React は触らない。
unlock はタイトル画面のボタンハンドラから同期的に `runtime.unlockAudio()` を呼ぶ
（`await` を挟むとジェスチャ資格が切れるため）。

### 演出時間はコアが持ち、CSS に渡す

```ts
case 'bg':
  state.snapshot.bg = step.name
  await this.perform(step.fade ?? 0)   // phase='performing' にして fade ms 待つ
```

```tsx
<div style={{ transitionDuration: `${state.view.fadeMs}ms` }} />
```

**`transitionend` で演出完了を判定しない。** 理由は2つ。

1. タブが非アクティブなときなど、発火が保証されない状況がある
2. 判定が DOM 側にあると、描画を伴わないリプレイで完了を検知できない

時間の権威をコアに置くことで、「リプレイは演出の待ち時間をゼロにした通常再生」が
**待ち時間に 0 を渡すだけ**で実装される。コアにも描画層にもリプレイ専用の分岐が入らない。

## 4. セーブ位置の定義（仕様の精密化）

実装に踏み込んだ結果、engine-spec の記述に定義されていない点が2つ見つかった。

### `index` は「セーブした瞬間に表示していた本文ブロック」

engine-spec は `index` を「本文ブロック連番」としか書いておらず、
それが「最後に表示したブロック」か「次に表示するブロック」かを定義していなかった。

**「セーブした瞬間に画面に表示されていたブロック」と定義する。**
ロードとはセーブ時の画面を再現することであり、次のブロックから始めると
読者が最後に見ていた文が画面から消えて話が進んだ状態になるため。

```
セーブ時: i:1 を表示中     → { "index": 1 }
復元:     i:0 をリプレイ   → i:1 を表示してクリック待ち
```

engine-spec の「`index` ブロック分リプレイ」という記述はこの定義と整合する。

### セーブ可能点はページ送り待ちを含む

engine-spec は「本文を表示し終えてクリック待ちしている瞬間」と書いているが、
1つの本文ブロックが複数ページに分かれる場合、途中ページのクリック待ちが
これに該当するかが不明だった。

**含める。** ページ送り待ちも「静止した画面で次のクリックを待っている」状態であり、
セーブ可能点を限定した本来の意図（演出途中の復元という問題を発生させない）は満たされる。
`phase` は `performing / typing / waiting` の3つで足り、ページ送り専用の状態は要らない。

### ページはセーブデータに現れない

ページ分割は**実行時に読者の環境で決まる**（画面サイズ、文字サイズ、フォント）。
同じブロックがスマホで3ページ、PCで1ページになる。

したがってページ番号を保存すると、**スマホでセーブしたデータをPCで開いた瞬間に
存在しないページを指す**ことになる。ページはセーブデータに入れられる種類の情報ではない。

結果として、途中ページでセーブすると復元時はそのブロックの先頭ページに戻る。
読み直しは最大でも1ブロック分に収まり、書き手が改行を入れれば短くできる。

`i`（本文ブロック連番）はビルド時に確定する静的な値であり、
ページ送りが発生しても一切変化しない。ページは `view` 層にだけ存在する。

### 却下した案

| 案 | 却下理由 |
|---|---|
| 最終ページのクリック待ちだけをセーブ可能点とする | `index` の定義を上記のとおり確定させると、復元地点は結局ブロック先頭になり、この案の利点（読み直しゼロ）は成立しない。`phase` に `paging` が1つ増え、セーブできる場所が減るだけになる |
| ページ番号をセーブデータに含める | 環境依存のデータになり、別端末・別文字サイズで開いた瞬間に破綻する |
| `index` を「次に表示するブロック」と定義する | セーブ時に見ていた文が復元時に画面から消える |

## 5. 台本コンパイラとビルドパイプライン

### Vite プラグインとして実装

```ts
// tools/wn-compile/index.ts
transform(code, id) {
  if (!id.endsWith('.wn')) return
  return { code: `export default ${JSON.stringify(compile(code, id))}` }
}
```

型は `src/engine/core/script.ts` に定義し、コンパイラがそれを import する。
**依存の向きは tools → engine の一方向。**

### パーサ

行指向で、1行を1回だけ分類する。

| 行頭 | 分類 |
|---|---|
| `#` | コメント（捨てる） |
| `=` | シーン宣言 |
| `@` | 演出 |
| `>` | 話者（次の1本文ブロックに適用） |
| 空行 | 無視 |
| **それ以外すべて** | **本文** |

第一原則がここに効く。**本文がデフォルトの分類であり、その分類には失敗が存在しない。**
記法を1つも使わない原稿は全行が本文になって必ず通る。

したがって**パースエラーは `@` で始まる行にしか発生しない。**
未知の命令・引数の不足・引数の型違いを、ファイル名と行番号付きで落とす。
命令は14個の有限集合なのでタイポを検出できる。
話者名（`>ミカ`）は自由文字列なので検出しない（engine-spec の「意図的に実装しないもの」）。

シーン名の重複もビルドエラーとする。セーブが `{scene, index}` で位置を指すため、
シーン名は作品内で一意でなければならない。

### 素材の存在チェックと拡張子の解決

`@bg rain_street` に対して `public/bg/rain_street.*` を探し、見つかったパスを埋める。

```json
{ "t": "bg", "name": "rain_street", "src": "bg/rain_street.webp", "fade": 800 }
```

素材の置き忘れが実行時の404ではなくビルドエラーになり、
実行時に拡張子を推測しなくて済む。素材を webp から png に差し替えても台本は変わらない。

**素材マニフェスト（シーンごとの使用素材一覧）は出力しない。**
ここで簡単に集計できるが、プリロードは未着手の残事項であり、
使う実装がない出力を作らない。必要になったら十数行で足せる。

### 既読ハッシュ

engine-spec の定義どおり `シーン名 \n 話者名 \n 本文` を SHA-256 して先頭12桁。
Node の `crypto` でビルド時に計算し、`h` に埋める。実行時にハッシュ計算のコードは存在しない。

### 拡張子は `.wn` を維持する

**`.wn` = web novel。エンジン名が決まっても変更しない。**

`.txt` も検討したが却下した。台本は `@bg`、`= scene`、`>話者` という構文を持つ独自言語であり、
**プレーンテキストが通るのはこの言語が `.txt` を包含しているからであって、
`.txt` と同じだからではない。** 包含する側に包含される側の拡張子を付けるのは関係を逆に表示している。

実務上も、判定が `id.endsWith('.wn')` で済む（`.txt` ならパス正規表現になり、
台本を複数ファイルに分割した時点で直す必要が出る）、
`declare module '*.wn'` が他の import と衝突しない、
将来のシンタックスハイライトを拡張子で関連付けられる、という利点がある。
Ren'Py の `.rpy`、TyranoScript の `.ks`、Ink の `.ink` と同じ慣行でもある。

なお第一原則（記法なしの原稿がパースエラーにならない）は**言語仕様の性質**であり、
ファイル拡張子について何も規定していない。両者を結びつける論証は成立しない。

### 開発ビルド限定の開始位置指定

```
localhost:5173/novelA/?scene=商店街&index=12
```

`import.meta.env.DEV` で囲み、本番ビルドには一切含めない。
`index` は省略可能で、省略時は 0（そのシーンの最初の本文ブロック）。
**`index` はシーン内のローカルな連番なので、`scene` と対で指定する必要がある。**

実装は開始位置まで作品先頭から演出スキップでリプレイするだけで、
セーブの復元と同じ経路を通る。開発用の専用コードがほぼ増えない。

台本の変更はフルリロードで反映する（HMR で進行状態を保つのは複雑さに見合わない）。
その代償をこの機能が打ち消す。

## 6. シーンの粒度

**実用上は章〜節。細かく切れるのは選択肢であって推奨ではない。**

`script-syntax.md` は「シーンを細かく切るコストがゼロになる」と書いているが、
これは細かく切っても状態がリセットされないという意味であり、細かく切るべきという意味ではない。

細かく切る利益は改稿時のセーブずれが狭い範囲に収まることだけで、
リプレイの長さは待ち時間ゼロなので実質無コストである。
一方でシーン名は作品内で一意でなければならず、命名のコストは実在する。

**シーン名の自動採番は採用しない。** シーンを1つ挿入した瞬間に以降の番号がずれ、
既存セーブが全部壊れる。名前の安定性がセーブの安定性そのものである。

## 7. テスト方針

コアが React にも DOM にも依存しないため、Vitest で jsdom なしにテストできる。
engine-spec の不変条件が、そのままテストケースの一覧になる。

| テスト | 内容 |
|---|---|
| **第一原則** | 記法を1つも含まないプレーンテキストが、全行本文としてパースされる |
| **リプレイの決定性** | 同じセーブから2回復元して `EngineState` が完全一致（不変条件2） |
| セーブのラウンドトリップ | save → load で `snapshot` が一致する |
| 連番の耐性 | 演出行を挿入しても既存セーブの `index` が指す本文が変わらない |
| 既読ハッシュの安定性 | 本文を変えたブロックだけ未読に戻り、他は無傷 |
| `@bgm` の意味論 | 同名再指定で鳴らし直さない |
| 各命令のパース | 14命令それぞれが期待する step になる |
| 話者のスコープ | `>` が直後の1ブロックにだけ効く |
| コンパイルエラー | 未知の命令・シーン名の重複が行番号付きで落ちる |

これらはセーブ互換性に関わるため「実装したら壊れていた」では手遅れになる性質のもので、
テストで固定する価値が大きい。

`storage.ts` を interface にするのは localStorage → IndexedDB の差し替えのためでもあるが、
テストでインメモリ実装を差せることのほうが日常的に効く。

## この決定が後段に与える制約

| 制約 | 影響先 |
|---|---|
| ビルド単位は作品ごと | デプロイ手順、CI を組む場合の構成 |
| 作品IDは作品側が明示的に渡す | `boot()` のシグネチャ、ストレージキー |
| `EngineState` は3層 | 命令を追加するたびに層を選ぶ。engine-spec 不変条件4に追記が要る |
| 演出時間はコアが持つ | 新しい演出命令も同じ経路を通す。CSS 側に時間を書かない |
| `index` は表示中のブロック | セーブ・ロード・開発用の開始位置指定で一貫させる |
| 依存の向きは tools → engine | 台本の型を変えるときはエンジン側から |
