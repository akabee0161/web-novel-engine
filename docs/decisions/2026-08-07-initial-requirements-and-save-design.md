## この文書の位置づけ

これは完全な設計書ではない。web-novel-engine の立ち上げにあたって、
**台本を書き始める前に確定させておく必要があった決定だけ**を記録したもの。

命令セットの全体像、技術スタック、素材管理などは未確定であり、
台本フェーズ以降で決める（末尾の「未確定事項」を参照）。

この文書の決定は、台本の書き方（シーンの区切り方、変数宣言の位置など）に
直接制約を与える。台本を書くときは本書を参照すること。

## 前提

### 用途

自分が書くノベルを載せるための道具。想定利用者は自分ひとり。

### 目標

1. **自分の台本が実際に必要とした機能だけを作る。**
   機能の要否を決めるのは、既存エンジン（Ren'Py, TyranoScript, WebGAL 等）の機能表ではなく、
   自分が書いた台本。台本に出てこない機能は作らない。
2. **エンジンの命名はサイトブランド（ankardo）から独立させる。**

### 進め方の原則

機能一覧から設計を起こさない。**実際の台本を先に書き、そこから必要な命令セットを確定させる。**

## 確定した要件

| 項目 | 決定 |
|---|---|
| 画面形式 | ADV 型（画面下部にメッセージ枠、中央に立ち絵） |
| 分岐 | 初期実装は一本道。将来の分岐・フラグ導入に耐える設計にする |
| 台本 | 1ファイル完結。無記号行＝本文、行頭 `@` ＝演出 |
| 作品規模 | 短編から始め、中長編に耐えること |
| 配信形態 | 静的サイトとしてビルド・公開。サーバなし |
| セーブ保存先 | 端末ローカル |

### 台本フォーマットの第一原則

**無記号のプレーンテキストが、そのままで最小の台本として成立すること。**

執筆フローは「まず普通に文章を書く」→「そこに演出を足していく」。
したがって演出記法は、文章に対する後付けの差分でなければならない。
記法なしの原稿がパースエラーになる言語仕様は採らない。

```
── 執筆直後（これだけで動く） ──
雨は、まだ降っていた。
ミカ「……帰ろうか」
彼女は僕の袖を引いた。

── 演出を足した後 ──
@bg rain_street fade:800
@bgm rain
雨は、まだ降っていた。
@show mika
ミカ「……帰ろうか」
@wait 500
彼女は僕の袖を引いた。
```

（`@` の具体的な命令名・引数の書式は未確定。台本フェーズで確定させる）

## 保存設計

### 用語

- **本文ブロック** — メッセージ枠に表示されてクリック待ちになる1回分。
  セーブの連番が数える単位であり、既読ハッシュの単位でもある。
- **シーン** — 台本上の名前付きの区切り。セーブ位置の粗い座標であり、
  復元時のリプレイ開始点。

### 採用した表現

セーブ位置は **シーンID ＋ シーン入口スナップショット ＋ 本文ブロック連番** で表す。

```json
{
  "scene": "商店街",
  "snapshot": {
    "bg": "rain_street",
    "bgm": "rain",
    "sprites": [{ "id": "mika", "expr": "normal", "pos": "center" }],
    "speed": "normal",
    "flashback": false,
    "vars": { "met_mika": true, "trust": 2 }
  },
  "index": 12
}
```

復元手順は「スナップショットを復元 → シーン内を演出スキップで `index` ブロック分リプレイ」。

スナップショットの対象は「シーン境界で持ち越される状態すべて」。
シーンは状態をリセットしないため、`@speed` や `@flashback` のように
明示的に戻すまで持続する演出状態も含める。
詳細は [スクリプト構文リファレンス](../script-syntax.md) を参照。

#### 連番は本文ブロックだけを数える

`@` で始まる演出行はカウントしない。これによって、演出を何行挿し込んでも
既存セーブの位置は動かない。

セーブが壊れるのは「同一シーン内に**本文ブロック**を挿入・削除したとき」だけで、
被害はそのシーン内に閉じる（章をまたいで飛ぶことはない）。

#### セーブが解決できない場合の扱い

| 状況 | 挙動 |
|---|---|
| `index` がシーンの本文ブロック数を超える（本文が削除された） | そのシーンの最後の本文ブロックにクランプする |
| `scene` が現在の台本に存在しない（シーン名の変更・削除） | ロード失敗として扱い、読者に明示する。黙って別の位置に飛ばさない |

シーン名の変更は作者の明示的な操作なので、セーブが壊れること自体は受け入れる。
ただし**壊れたことを隠さない**。読者が知らないうちに別の場所へ飛ばされるほうが害が大きい。

#### スナップショットはビルド時計算ではなくランタイム取得

シーンに入った瞬間に、エンジンの状態を丸ごとスナップショットしてメモリに保持する。

一本道であれば各シーン先頭の状態はビルド時に静的計算できるが、分岐が入ると
同じシーンに複数経路から到達しうるため一意に決まらない。
ランタイム取得なら経路に依存しないので、**分岐を追加してもセーブ設計を変更する必要がない。**

#### 変数はシーン入口の値を保存する

スナップショットに入る `vars` は「セーブした瞬間の値」ではなく「シーンに入った瞬間の値」。

これにより、リプレイ中に `@set trust = trust + 1` のような非冪等な操作を通過しても、
入口の値から再実行されるので正しい値に着地する。
セーブ時点の値を持つ設計だと、リプレイ中に状態変更命令を実行すべきか否かを
命令ごとに区別する必要が生じ、バグの温床になる。

**この設計により、リプレイ処理は「演出の待ち時間をゼロにするだけ」の単純な処理になる。**
命令の種類を区別しない。

#### 変数の前方互換

変数は台本側で初期値を宣言する。ロード時は「宣言済みデフォルト値にセーブ値を上書きマージ」する。
あとから変数を追加しても、旧セーブにその変数が無いだけなのでデフォルト値が入り、壊れない。

### セーブ可能点の限定

**セーブ可能なのは「本文を表示し終えてクリック待ちしている瞬間」だけ。**

- フェード中・トランジション中にオートセーブを打たない
- 演出中は手動セーブUIを開かせない
- 文字送り中にセーブが要求されたら、文字送りを完了させてからセーブする

「演出途中の任意時点セーブ・復元」は解かずに消す。
復元すべき状態が「静止した画面」だけになり、問題が丸ごと消滅する。
読者体験の損失は実質ゼロ。

### 既読管理

**既読は本文ハッシュの Set で持つ。セーブとは完全に独立した仕組み。**

#### ハッシュの定義

入力は次の3つを連結した文字列。

```
シーン名 \n 話者名 \n 本文
```

ハッシュ関数は SHA-256、先頭12桁（48bit）を採る。
本文1万ブロックでも衝突確率は 1000万分の1以下で、実用上ゼロ。

シーン名を混ぜるのは、「……」「うん」のような短い行が作品中で繰り返し出現するため。
本文だけでハッシュすると、序盤の「うん」を読んだ時点で終盤の「うん」まで既読になる。
シーン名で区切れば、その混同がシーン内に閉じる。

（同一シーン内に同じ話者の同じ本文が複数回出る場合は依然として同一視される。
影響はスキップが1ブロック余分に進む程度なので、対策しない）

#### ハッシュはビルド時に計算する

実行時にはハッシュ計算をしない。台本をコンパイルした時点で各本文ブロックに埋め込む。

```json
{
  "id": "商店街",
  "steps": [
    { "t": "bg",   "name": "rain_street", "fade": 800 },
    { "t": "bgm",  "name": "rain" },
    { "t": "text", "i": 0, "h": "a3f91c22b0d4", "body": "雨は、まだ降っていた。" },
    { "t": "show", "id": "mika", "pos": "center" },
    { "t": "text", "i": 1, "h": "7e05fa19c883", "speaker": "ミカ", "body": "……帰ろうか" },
    { "t": "text", "i": 2, "h": "c1d80e4a6f37", "body": "彼女は僕の袖を引いた。" }
  ]
}
```

`i` がセーブ用の本文ブロック連番、`h` が既読用のハッシュ。
演出ステップ（`bg` / `show`）に `i` が振られていないことが、演出行挿入への耐性を生む。

#### 実行時の処理

```js
readSet.add(step.h)   // 本文ブロック表示時
readSet.has(step.h)   // 既読判定
```

シーンも位置も参照しない。連番で持つより実装が単純。

#### 記録タイミング

**セーブ操作とは無関係に、本文を表示した瞬間に記録する。**
セーブせずにブラウザを閉じても既読は残る。
「セーブしないと既読が付かない」設計は、読者が意図せず既読を失うので採らない。

#### 改稿時の挙動

本文を書き換えるとハッシュが変わるので、そのブロックだけ未読に戻る。
他のブロックの既読は無傷。改稿された文が未読になるのは正しい挙動。

本文ブロックを新規挿入した場合、以降のブロックの `i` はずれるが `h` は1つも変わらない。

#### セーブと既読の対比

| | セーブ | 既読 |
|---|---|---|
| 形 | 点（現在地＋状態） | 集合 |
| 順序 | 意味を持つ | 意味を持たない |
| 更新 | 上書き | 累積のみ |
| 単位 | スロットごとに独立 | 作品ごとに1つ、全スロット共通 |
| 編集耐性 | 本文挿入でずれる | 挿入しても無傷 |

要求が異なるため、別々の表現を使う。

### ストレージ

セーブデータとシステムデータを分離する。

```
wn:<作品ID>:save:1        ┐
wn:<作品ID>:save:2        ├ セーブデータ（スロットごとに独立）
wn:<作品ID>:save:auto     ┘
wn:<作品ID>:system        ← システムデータ（作品ごとに単一・全スロット共通）
```

**システムデータの内容**

- 既読本文のハッシュ Set
- 文字送りの設定、音量などの設定
- （将来）到達したエンディングの集合、CG/BGM 回収状況

**文字送り設定は2階建てにする**

- モード: 逐次表示 / 一括表示
- 速度: 逐次表示のときの基準速度

台本の `@speed` は基準速度に対する**相対倍率**として働く。
読者が速度を上げていても `@speed slow` の箇所は相対的に遅くなり、
演出の意図と読者の好みが両立する。

**ただし一括表示が選ばれている間は `@speed` を完全に無視する。**
一括表示を選ぶ読者は文字が流れること自体を避けたいのであり、
そこに演出として文字送りを差し込むのは読者の意思に反する。

分離の利点: セーブスロットを削除しても既読は消えない。既読だけリセットもできる。
将来セーブをエクスポート/インポートしても既読が付いてこない。

**実装方針**

- ストレージ層は差し替え可能なインターフェース越しにアクセスする
- 初期実装は localStorage
- 書き込みはメモリ上の Set を数秒おき、および `pagehide` でまとめて書き出す
  （毎クリックで全体を JSON 化しない）
- 中長編で容量が問題になったら IndexedDB に差し替える。
  短編のうちは数KBに収まるため、先行実装しない

## 設計上の不変条件

以下はエンジンのコア設計を縛る条件であり、後から追加することができない。

1. **エンジンの状態はスナップショット可能な1箇所に集約する。**
   個別の演出モジュールが内部に復元不能な状態を隠し持ってはならない。
2. **シーン内のリプレイは決定論的でなければならない。**
   台本中で乱数を使う場合、乱数シードもスナップショットに含める。
   （乱数機能自体の実装は後回しでよい）
3. **本文ブロックの連番は、本文ブロックだけを数える。**
4. **シーン境界で持ち越される状態は、すべてスナップショットに含める。**
   命令を追加するときは、それが持ち越す状態を持つかどうかを判断すること。
   怠ると、その演出だけ復元されないセーブができる。

## 意図的に採用しなかった案

| 案 | 却下理由 |
|---|---|
| 命令インデックスによるセーブ | 1行挿入で既存セーブが壊れる（前提として除外） |
| 本文ハッシュによるセーブ位置アンカー | 本文挿入に強いが推敲に弱い。採用案Aの被害が「同一シーン内で数ブロックずれる」程度に収まるため、3段フォールバックの複雑さに見合わない。セーブに `hash` フィールドを後から足しても旧セーブは壊れないので、将来の選択肢は残る |
| 明示的チェックポイントのみ | 最も壊れないが、読者が常に直前のチェックポイントまで巻き戻される |
| シーン入口状態のビルド時静的計算 | 一本道でしか成立せず、分岐追加時に設計変更が必要になる |

## 未確定事項

台本フェーズ以降で決める。

記法と命令セットは [スクリプト構文リファレンス](../script-syntax.md) で暫定確定した。
残っているのは以下。

- 変数の宣言記法（分岐を導入するときに決める）

- バックログ
- スキップUI（既読データの記録は初期実装に含むが、それを使う機能は後回し。

- 作品IDの与え方、複数作品の扱い

## 初期実装に含める / 含めない

既読まわりは3つに分かれる。混同しないこと。

| 要素 | 初期実装 |
|---|---|
| 既読をハッシュで表現する | 含む（連番より単純なため。将来のための前倒しではない） |
| 既読を記録する（表示時に Set へ追加・保存） | 含む（数行で済む。後回しにすると、スキップ実装時点で既読データがゼロから始まる） |
| 既読を使う（スキップ機能・UI） | 含まない |
| IndexedDB への差し替え | 含まない |
