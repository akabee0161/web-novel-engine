# 実装着手前に確定させた10項目

- 日付: 2026-08-08
- 状態: **凍結。** 執筆時点のスナップショットであり、以後書き換えない
- 契機: [実装計画](../implementation-plan.md)を18タスクに分解する過程で、
  [エンジン仕様](../engine-spec.md) / [実装構成](../architecture.md) に定義がない点が10個見つかった

実装に入ると、これらは「決める」のではなく「なんとなくそう書いた」になる。
コードが先に固まってから仕様を書き起こすと、決定の理由が残らない。
だから着手前にまとめて確定させた。

10項目のうち3つ（1・2・10）は既存ドキュメントの記述を**変える**。
残り7つは既存の記述と矛盾せず、新たに決めるだけのもの。

---

## 1. 行頭の命令は10種類（ドキュメントの誤記）

`status.md` と [初期要件の決定記録](2026-08-07-initial-requirements-and-save-design.md) は
「命令は14個」と書いていたが、実際に列挙されているのは10個だった。

```
@title  @protagonist
@bg  @bgm  @se
@show  @hide
@wait  @speed  @flashback
```

`@bgm stop` / `@hide *` / `@speed slow|normal` / `@flashback on|off` を
別命令として数えた結果と思われる。**数えるのは行頭の命令名**とし、10種類が正しい。

引数の値まで数えると、`@speed` に値を1つ足すたびに命令数が増えることになり、
数字が「エンジンの表面積」を表さなくなる。

→ `status.md` を修正した。decisions は凍結文書なので触らない。

## 2. 素材パスの解決は assets テーブルに統一する

`architecture.md` は「`public/<種別>/<名前>.*` を探し、**見つかったパスを step の `src` に埋める**」
と書いていたが、**立ち絵ではこれが成立しない。**

`@show mika smile` は表情を省略できる仕様であり（`@show mika pos:left` は表情を維持する）、
その時点の表情はビルド時に確定しない。静的に追跡すること自体はできるが、分岐が入ると
到達経路が一意でなくなる。engine-spec がスナップショットの静的計算を却下したのと同じ理由で、
同じ壁に当たる。

**コンパイラは `public/` をスキャンして論理名 → 実パスの表を1つ出し、実行時に引く。**

```json
"assets": {
  "bg/clubroom_day":   "bg/clubroom_day.svg",
  "chara/mika_normal": "chara/mika_normal.svg",
  "bgm/daily":         "bgm/daily.wav"
}
```

存在チェック（ビルドエラー）は**台本に書かれた引数**に対して行う。
表情を省略した `@show` はチェックできないため、実行時に表が引けなければ
`console.warn` して立ち絵を出さない。台本に書いてある素材の置き忘れは
これまで通りビルドで落ちる。

**これはプリロード用マニフェストではない。**
[初期要件の決定記録](2026-08-07-initial-requirements-and-save-design.md)が
「出力しない」と決めたのはシーンごとの使用素材一覧であり、パス解決表とは別物。
プリロードは未着手のまま。

→ `architecture.md` の「素材の解決」を書き換えた。

## 3. 既読ハッシュの「話者名」は台本の `>` の引数そのもの

engine-spec のハッシュ入力 `シーン名 \n 話者名 \n 本文` の話者名の定義。

| 台本 | 話者名 |
|---|---|
| `>ミカ` に続く本文 | `ミカ` |
| `>` だけ（伏せる） | 空文字列 |
| `>` がない（地の文・主人公の発話） | 空文字列 |

**`@protagonist` の表示名を混ぜない。** 混ぜると、主人公名を変えた瞬間に
主人公の発話が全部未読に戻る。名前は表示の都合であって本文の同一性ではない。

## 4. オートセーブはセーブ可能点に到達するたびに打つ

engine-spec はキー `wn:<作品ID>:save:auto` を定義していたが、いつ打つかを書いていなかった。

**`phase` が `waiting` になった瞬間に打つ。**

セーブ可能点の定義がそのままオートセーブのタイミングになるため、
「フェード中にオートセーブを打たない」という制約が、条件を1つも足さずに構造的に満たされる。

終端（`phase: 'ended'`）では打たない（項目10を参照）。

## 5. 文字送り中のクリックは全文を即座に表示する

クリックすると全文を表示して `waiting` に移る。次のブロックには進まない。

engine-spec は「文字送り中にセーブが要求されたら文字送りを完了させてからセーブする」と
書いており、すでにこの挙動を前提にしていた。明文化しただけ。

## 6. 文字送りの実値

| 項目 | 値 |
|---|---|
| 基準 | 40ms / 文字 |
| 読者設定（速度） | 遅い ×1.5 ／ 普通 ×1.0 ／ 速い ×0.5 |
| 読者設定（モード） | 逐次表示 ／ 一括表示 |
| `@speed slow` | さらに ×2.0 |
| `@speed normal` | ×1.0 |

一括表示のときは `@speed` を完全に無視する（engine-spec の既定）。

40ms は「普通」で1秒あたり25文字。実際に読んで調整する前提の初期値であり、
定数として1箇所に置く。

## 7. ページ分割の測定は UI が行い、境界を数値でコアに渡す

コアは DOM を触れないため、テキスト測定は UI 層の責務になる。

UI が Range API で「枠に収まる文字数」を測り、境界の配列をコアに渡す。

```ts
runtime.setPageBreaks(breaks: number[])   // [0, 42, 87] のような文字位置
```

コアは現在ページの文字範囲だけを文字送りの対象にする。
受け取るのが数値の配列だけなので React / DOM 非依存は保たれ、
テストでは境界を直接渡せる。

## 8. テストは `tests/` にソースをミラーして置く

`architecture.md` のディレクトリ構成図にテストの置き場所がなかった。

```
tests/
├── compile/parse.test.ts
├── core/runtime.test.ts
└── ...
```

`vite.config.ts` が環境変数 `NOVEL` を要求するため、テストは `vitest.config.ts` を分ける。
`NOVEL` を指定しないとテストが走らない、という状態を避けるため。

## 9. リプレイ中は SE を鳴らさない

engine-spec は「リプレイは演出の待ち時間をゼロにした通常再生」と書いているが、
これを音声にそのまま適用すると**リプレイ中に SE が全部鳴る。**
ロードした瞬間にドアの音と紙の音と電話の音が一度に鳴ることになる。

| 種別 | リプレイ中 |
|---|---|
| `@se` | 鳴らさない（状態ではなく発火のため） |
| `@bgm` | `snapshot.bgm` を更新するだけ。リプレイ終了時に1回だけ実際の再生と同期する |

同期処理 `audio.syncBgm(name)` は「今鳴っているものと同じ名前なら何もしない」であり、
これは `@bgm` の同名再指定の意味論そのもの。通常再生でも同じ関数を通すため、
リプレイ専用の分岐は `if (!replaying)` の1箇所に収まる。

「リプレイ専用の分岐がどこにも入らない」という architecture の主張は、
音声に関してだけは成立しない。**`@se` が状態ではなく発火だから**であり、
これは待ち時間をゼロにすることでは吸収できない。

## 10. `phase` に `ended` を足す

`architecture.md` の `phase` は `performing / typing / waiting` の3つだったが、
**台本の終端に到達した状態がこれで表せない。**
`waiting` のままにすると、クリックで進めるように見えて何も起きない画面になる。

```ts
phase: 'performing' | 'typing' | 'waiting' | 'ended'
```

**`ended` はセーブ可能点ではない。** 終端でオートセーブを打つと、
次回ロードしたとき最後の1ブロックだけ読める状態になる。

→ `architecture.md` の3値に1つ足した。
