# 原稿 → `.wn` 変換スキル 設計

- 作成: 2026-08-12
- 状態: 設計確定。実装前
- 対象: `.claude/skills/novel-to-wn/`（新規）、`novels/`（2作目のスキャフォールド先）

> これは作成時点のログである。実装後に仕様が変わっても遡って更新しない。
> 現在の確定仕様は `docs/engine-spec.md` / `docs/architecture.md` / `docs/script-syntax.md` にある。

## 背景

初期実装（Task 1-18）と縦持ちレイアウト対応が完了し、1作目 `kieta-ippen` で通しの動作は確認済み。
次の展開として2作目（本番想定の実在作品）を用意することになったが、`novels/` にはまだ存在しない。

執筆そのもの（プロット・地の文の創作）は別リポジトリ `../ai-writing` が担当する。
そちらから受け取るのは「地の文とカギ括弧の会話が混ざった、メタ情報なしの普通の小説テキスト」であり、
話者名・シーン境界・演出（背景/BGM/立ち絵など）はいずれも明示されていない。

`docs/script-syntax.md` の第一原則により、無記号の地の文と `「」` の会話はそのままで
最小の `.wn` として成立する。つまり構造変換の大部分はゼロコストで、
支援が要るのは「原稿にない情報を新たに判断して足す」部分——話者指定・シーン区切り・演出——に絞られる。

この設計は、その変換作業を助ける Claude Code スキルを定義する。

## 決定

### 1. AI が一気に下書きを作り、人間が後からレビューする

**採用。** 判断が必要な変換部分（話者・シーン・演出）を機械的なルールだけで自動化するのは
原稿の文脈理解を要するため無理がある。かといって全て手作業では支援にならない。
AI が対話的に原稿を読み、`.wn` ドラフトを一気に作成し、確信度が低い箇所には
`# TODO: 話者?` のようなコメントを残して人間のレビューに委ねる。

検討した他の案:

| 案 | 採らない理由 |
|---|---|
| 構造部分のみ自動化する決定的な CLI ツール（`tools/` に実装） | 話者・シーン・演出の判断が結局すべて手作業に残り、支援効果が薄い |
| まず手作業で2作目を変換してから設計する | 今回は先に支援ツールを用意し、2作目自体をその実地検証に使う方針を採る |

### 2. Claude Code のプロジェクトスコープスキルとして実装する

**採用。** `.claude/skills/novel-to-wn/SKILL.md` を新設し、`/novel-to-wn <原稿パス> <作品ID>` で呼び出す。
引数省略時は対話で確認する（既存の `novel-write` スキルと同じパターン）。

通常のコード（`tools/` 配下のスクリプト等)ではなくスキルとして実装する理由:

- 話者推定・シーン区切り・演出提案はいずれも文脈理解を要する判断であり、決定的なロジックで書けない
- `docs/script-syntax.md` は「話者の誤字検出」「話者の付け忘れ検出」を意図的に非実装とし、
  「最終確認は人間または AI が行う」と明記している。本スキルはその想定済みの役割を担う

### 3. 出力先は `novels/<作品ID>/script.wn` に直接書き、`tools/wn-compile` で自己検証する

**採用。** 別の下書きファイル（`draft.wn` 等）を経由すると、人間が明示的に取り込むステップが
1つ増えるだけで実質的な安全性は変わらない。`tools/wn-compile` の既存パーサで
構文エラー・シーン名重複を自己検知・自己修正してから人間のレビューに渡す。

### 4. 作品ディレクトリの新規スキャフォールドもスコープに含める

**採用。** 2作目は `novels/` にまだ存在しない。`script.wn` の変換だけでは
`NOVEL=<作品ID> npm run build` が通らず、実地検証まで到達しない。
`kieta-ippen` を雛形に `novel.config.json` / `main.ts` / `public/`（ダミー素材）を
複製・作品ID差し替えする工程もスキルに含める。

## ワークフロー

1. **入力確認** — 原稿パスと作品IDを受け取る。作品IDが既存で `script.wn` が既にある場合は上書き確認を取る
2. **スキャフォールド** — 作品IDが未存在なら `kieta-ippen` を雛形に `novel.config.json` / `main.ts` / `public/`
   （ダミー素材）を複製・作品ID差し替え
3. **ブロック化** — 原稿を改行単位で本文ブロックへ変換。第一原則（無印の地の文・`「」` はそのままで
   最小の台本として成立する）により、構造変換の大部分はここで完了する
4. **話者付与** — 「〜と〇〇が言った」等の文脈手がかりから話者を推定し、主人公以外の発話に
   `>名前` を挿入する。判断が割れる箇所は `# TODO: 話者?` を残す
5. **シーン区切り** — 章見出しや場面転換の手がかりから `= scene <一意な名前>` を提案挿入する。
   既存シーン名との重複もチェックする
6. **演出の仮提案** — 場所描写→`@bg`、人物の登場・退場→`@show`/`@hide`、回想描写→`@flashback`、
   間の描写→`@wait` など、地の文の手がかりから妥当な命令を仮挿入する。確信度が低い箇所は
   `# TODO: bg?` 等のコメントを残す
7. **作品メタ** — `@title` / `@protagonist` をユーザーに確認して先頭に付与する
8. **自己検証** — `tools/wn-compile` のパーサでビルドし、構文エラー・シーン名重複を検知したら自己修正する
9. **レビュー依頼** — TODO コメントの一覧と変更概要を提示して終了する。**コミットはしない**
   （`CLAUDE.md` の「コミット前に一度止めて確認を取る」を踏襲する）

## スコープ外

- BGM/SE/立ち絵の実素材そのものの用意（`assetsDir` の中身）
- プロット・地の文そのものの創作支援（`../ai-writing` の責務）
- 話者誤字検出・キャラクター登録（`docs/script-syntax.md` で意図的に非実装と明記済み）
- 既存 `script.wn` への差分マージ（今回は新規変換のみ。改稿ワークフローは対象外）

## エラーハンドリング／エッジケース

- 作品IDが既存かつ `script.wn` が既にある → 上書き確認を取ってから進める
- パーサがシーン名重複を検知 → スキルが自己修正して再検証する（人間には最終結果だけ見せる）
- 原稿に見出し記法（Markdown の `#` など）が混ざる場合の解釈は `SKILL.md` 側で明示的に定義する
  （`docs/script-syntax.md` の行頭 `#` はコメント構文なので、素通しすると本文が消える）

## 検証・成功基準

- 実際の2作目原稿で動かし、`NOVEL=<2作目ID> npm run build` が通ることを確認する
- 生成された `script.wn` を人間がレビューし、TODO コメントが実際に「人間の判断が要る箇所」に
  絞られているか確認する
- スキル自体は `src/` を変更しないため、`npm test` / `lint` / `typecheck` への影響は基本ない。
  ただし `SKILL.md` は `docs/script-syntax.md` を都度参照し、構文ルールを埋め込み複製しない
  （本文が変わったときに乖離しないため）
