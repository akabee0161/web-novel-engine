# モバイル縦持ちレイアウト 設計

- 作成: 2026-08-09
- 状態: 設計確定。実装前
- 対象: `src/engine/ui/**`、`src/engine/core/runtime.ts`、`src/engine/core/state.ts`

> これは作成時点のログである。実装後に仕様が変わっても遡って更新しない。
> 現在の確定仕様は `docs/engine-spec.md` と `docs/architecture.md` にある。

## 背景

PC ブラウザでの通読では問題がなかったが、スマートフォンの縦持ちで開くと
16:9 のステージが画面幅までしか広がらず、高さがその 9/16 の帯になる。
`docs/status.md` に「モバイルの縦持ち時の画面 — 未確定。16:9 をそのまま縮めると
小さすぎる。実際に読んでから決める」として保留されていた項目。実読により確定させる。

iPhone 14（390×844）での実測:

| | 現状 |
|---|---|
| ステージの高さ | 219px（画面の 26.0%） |
| 本文の文字サイズ | 10.1px |
| 1ページの行数 | 2 行 |

## 検討したが採らなかった選択肢

### 自動で横向きに固定する

**採らない。ブラウザでは実現できない。**

| 手段 | 不可の理由 |
|---|---|
| `screen.orientation.lock('landscape')` | iOS Safari が未対応。Safari 16.4 で `type` / `angle` / `onchange` は入ったが `lock()` は入っていない。対応ブラウザでも「フルスクリーン表示中のみ」の制約付き |
| Web App Manifest の `orientation: "landscape"` | PWA としてインストールされ standalone 表示のときだけ有効。ブラウザのタブでは効かない |
| CSS `transform: rotate(90deg)` で丸ごと回す | `docs/architecture.md` の「`transform` による一括拡縮は採らない（テキストがラスタライズ後に拡大され大画面で眠くなる）」に抵触する。加えてブラウザの URL バーは縦のままで見た目が壊れる |

Ren'Py などが横固定にできるのは**ネイティブアプリとしてビルドし OS のマニフェストで指定しているから**であり、
ブラウザで動く前提の本エンジンには同じ手が使えない。

### 立ち絵を本文枠に重ねる

**採らない。** 背景を 16:9 のまま保ったまま立ち絵だけ大きくする案だが、
上下比を 50:50 にすれば立ち絵は 371px（横持ちの 343px より大きい）になり、
重ねる動機そのものが消える。

### 背景エリアを縦に広げて `contain` で敷き、上下をぼかしで埋める

**採らない。** 画像は切れないが、鮮明に見える範囲は結局 26% のままで、
上下比を 50:50 にする目的を果たさない。

### 縦持ち専用の背景素材を用意する

**今回は作らない。** 切り抜きの問題は原理的に解消するが、
作品側に「縦用の絵を描く」義務が増える。
本エンジンの目標1（台本に出てこない機能は作らない）に照らして、
必要になってから入れる。**将来の逃げ道として記録に残す。**

## 決定

### 1. 縦持ちは上下分割にする

縦長ビューポートでは、ステージをビューポート全体に広げ、
**上に「場面」（背景＋立ち絵）、下に本文枠**を置く。レターボックスは使わない。
背景の下に残る空間は**すべて本文枠が使う**（黒のまま余らせない）。

### 2. 上下比は 50:50 に固定する

場面の高さは `.wn-scene` に書く `height: 50cqh`。
この `cqh` は `.wn-scene` 自身ではなく祖先コンテナ ＝ `.wn-stage`（＝ビューポート全体）に対して
解決されるため、画面高の 50% になる。端末によらずレイアウトは同じになる。

背景は 16:9 素材を `background-size: cover` / `background-position: center` で敷くため、
**枠に入りきらない左右は切り落とされる。これを許容する。**
切れる量は端末の縦横比によって変わる。

| 端末 | 画面 | 場面の枠 | 見える幅 | 切れる幅 | 立ち絵 |
|---|---:|---:|---:|---:|---:|
| iPhone SE (3rd) | 375×667 | 375×334 | 63% | 37% | 293px |
| iPhone 13 mini | 375×812 | 375×406 | 52% | 48% | 357px |
| iPhone 14 / 15 / 16 | 390×844 | 390×422 | 52% | 48% | 371px |
| iPhone 15 Plus | 430×932 | 430×466 | 52% | 48% | 410px |
| iPhone 16 Pro Max | 440×956 | 440×478 | 52% | 48% | 421px |
| Galaxy S22 | 360×780 | 360×390 | 52% | 48% | 343px |
| Pixel 7 / 8 | 412×915 | 412×458 | 51% | 49% | 403px |
| iPad mini（縦） | 744×1133 | 744×567 | 74% | 26% | 499px |
| iPad Pro 11"（縦） | 834×1194 | 834×597 | 79% | 21% | 525px |

1600×900 の素材を iPhone 14 で見ると、中央の 832×900 だけが見える。
左右それぞれ 384px が画面外になる。

**「上下比を固定する」と「切れる量を固定する」は両立しない。** 前者を採った。
読者が触れるのはレイアウトのほうであり、切れ方は元の絵を知らなければ気づかないため。

**焦点の自動判定（顔検出・サリエンシー検出）は行わない。** 常に中央。

### 3. 「場面」を独立したコンテナにする

現状、背景と立ち絵は `.wn-scene`（`inset: 0`）に置かれ、
立ち絵の `height: 88cqh` は `.wn-stage` を基準に解決している。
縦持ちでステージがビューポート全体になると、この基準では立ち絵が巨大化する。

`.wn-scene` に `container-type: size` を与え、立ち絵の基準を**場面**にする。
横持ちでは `.wn-scene` と `.wn-stage` が同寸のため、**結果は現状と完全に一致する**。

本文枠は `.wn-msg-area` というラッパで包み、
縦持ちでは場面の下に、横持ちでは現状どおり絶対配置にする。

```
.wn-stage          縦: 100vw × 100dvh   ／ 横: 16:9 レターボックス（現状のまま）
  .wn-scene        縦: height 50cqh     ／ 横: inset 0（現状と同寸）  ← container 化
    .wn-bg-layer   cover / center（変更なし）
    .wn-sprite     88cqh ← 「場面」基準になる
  .wn-msg-area     縦: 残り全部          ／ 横: 現状の枠位置に絶対配置  ← 新設
    .wn-messagebox
```

### 4. 寸法の倍率は変数 1 つにまとめる

`cqw` 基準の寸法は本文枠だけでなく、タイトル画面・履歴・セーブ・設定のパネル類にもある。
縦持ちではステージ幅が 390px しかないため、`.wn-panel` の `2.2cqw` は 8.6px、
タイトルのボタンは 9.4px になり、そのままでは全滅する。

ルールごとにメディアクエリで上書きすると 20 箇所以上の二重管理になる。
**倍率を変数に切り出す。**

```css
.wn-stage { --wn-u: 1cqw; }
@media (orientation: portrait) {
  .wn-stage { --wn-u: 1.7cqw; }
}
.wn-messagebox { font-size: calc(2.6 * var(--wn-u)); }
```

既存の数値（2.6 / 2.2 / 1.9 …）はそのまま係数として残るため、
**横持ちの見た目は完全に不変**である。縦持ちは 1.7 倍。

倍率 1.7 の根拠は、**同じ端末を横持ちにしたときの文字サイズに揃うこと。**
iPhone 14 のステージ幅は横持ちで 693px、縦持ちで 390px。比は 1.78 である。

| | PC（1280幅） | iPhone 14 横持ち（693幅） | iPhone 14 縦持ち（390幅・×1.7） |
|---|---:|---:|---:|
| 本文 `2.6` | 33px | 18.0px | 17.2px |
| 話者名 `2.2` | 28px | 15.2px | 14.6px |
| パネル本文 `2.2` | 28px | 15.2px | 14.6px |
| 角ボタン `1.8` | 23px | 12.5px | 11.9px |

比は端末により変わる（iPad mini は 1.52）ため、1.78 ではなく丸めた 1.7 を採る。

変数化から外れる例外は 5 つ。

| 対象 | 扱い |
|---|---|
| `.wn-body { height: 15cqw }` | 縦持ちは枠の残り全部（可変） |
| `.wn-sprite { height: 88cqh }` | 場面基準にする。構造の変更であって倍率ではない |
| `.wn-panel { width: 80cqw }` | 縦持ちは 92cqw |
| `.wn-slot` 系 | 係数 1.9 / 1.6 は ×1.7 でも 12.6px / 10.6px にしかならない。縦持ちでは列を積んで別に組む |
| ボタン類のタップ領域 | 最小 44px を別途確保する |

### 実装上の罠 — `--wn-u` を置く場所と使う場所

コンテナクエリ単位は、**その宣言を使う要素の祖先コンテナ**に対して解決される。
`--wn-u: 1cqw` を `.wn-stage` に置いても、`.wn-stage` 自身の幅にはならない。

未登録のカスタムプロパティはトークン列として置換され、**単位は使用側で解決される**ため、
`.wn-messagebox { font-size: calc(2.6 * var(--wn-u)) }` は
`.wn-messagebox` の祖先コンテナ ＝ `.wn-stage` に対して解決される。これは意図どおり。

**ただし `.wn-scene` の内側で `--wn-u` を使うと `.wn-scene` 基準になる。**
`.wn-scene` もコンテナだからである。場面の内側にあるのは背景と立ち絵だけで、
どちらも `--wn-u` を使わない（立ち絵は `cqh` を直接使い、それが場面基準であることが正しい）。
**場面の内側で `--wn-u` を使わないこと。**

`.wn-body` と `.wn-measure` は同じ幅・フォントサイズ・行間でなければならない
（`src/engine/ui/style.css` のコメント）。変数化によりこの 2 つが同じ式を共有するため、
**片方だけ直す事故が構造的に起きなくなる。**

### 5. 回転したときはクリック待ち中に再測定する

`docs/decisions/2026-08-09-implementation-decisions.md` の決定3
「画面サイズの変更は次の本文ブロックから反映する（resize での再測定は行わない）」を**覆す。**

決定3は「読者がブロックの途中で画面を回す頻度」を低く見積もった判断だった。
デスクトップのウィンドウリサイズは稀だが、**縦持ちを正式に支えるなら回転は日常的に起きる。**
再測定しない場合、縦→横で枠が狭くなると収まっていた文字が `overflow: hidden` で隠れ、
読者はその分を読めないまま次のブロックへ進む。

**古い決定記録は書き換えない。新しい決定記録を足して経緯を残す。**

#### 安全な瞬間に限定する

再測定は **`phase === 'waiting'`（クリック待ち）のときだけ**行う。
この瞬間は文字送りが終わっており画面が静止している。セーブ可能点と同じ条件である。

決定3が警告していた「`type()` が走り終えた文字範囲と表示する文字範囲が食い違う」破綻は、
`type()` が走っていないこの瞬間には起きない。

#### 起点を現在ページの先頭に固定する

決定3が却下した「ループが毎回 `view.pageBreaks` を読み直す」案は、
現在ページの番号が指す位置がずれるために退けられた。**起点を固定すればこれは消える。**

再測定するのは本文全体ではなく、**現在ページの先頭文字位置 `from` 以降だけ**とする。
読者がいま読んでいる位置が新しい区切りの先頭に必ず来るため、ずれようがない。

#### ページ番号は通し番号を保つ

`consumed`（回転までに読み終えたページ数。現在ページは含まない）を保持し、

- `total = consumed + 新しい区切りの数`
- `current = consumed + p`

縦持ちで「1 / 2」の 1 ページ目を読んでいて横に回すと、残りが 3 つに割れて「1 / 3」になる。
数字は単調に増え、戻らない。

#### 実装

コア（`src/engine/core/`）:

| 変更 | 内容 |
|---|---|
| `requestRepaginate()` を追加 | `phase === 'waiting'` かつリプレイ中でないときだけ、フラグを立ててクリック待ちを解く |
| `execText` のページループ | `while` で包み、`from` と `consumed` を保持する |
| `view.measureFrom` を追加 | 「どこから測るか」を UI に伝える。初回は 0 なので現状と同一 |
| `advance()` | 無変更。フラグの有無でクリックと再測定要求を区別する |

`waitForClick()` の呼び出しは `execText` のページループ 1 箇所だけなので、
他の待ちに影響しない。

UI（`src/engine/ui/`）:

- `window.matchMedia('(orientation: portrait)')` の `change` を購読して `requestRepaginate()` を呼ぶ
- **`resize` は使わない。** モバイルは URL バーの伸縮で `resize` が頻発するため、向きの変化だけを見る
- `MessageBox` の測定は既存のまま。`isWaitingForPageBreaks()` 駆動なので再測定要求でそのまま再入する

`waitForPageBreaks()` 内のリプレイ分岐は変えないため、
**リプレイ専用の分岐は 5 箇所のまま増えない**（`docs/status.md`）。

## 不変条件

実装がこれを崩していないことを検証で担保する。

1. **横持ちの見た目は一切変わらない。** 係数と `--wn-u` の積は現状の値と一致する
2. **背景素材の作り方は変わらない。** 16:9 のまま。`assetsDir` の規約も変わらない
3. **セーブデータの形式は変わらない。** ページ番号はセーブに入らない（`docs/status.md` の前提 9）ため、
   縦横を切り替えても保存済みデータは壊れない
4. **`src/engine/core/**` は DOM を import しない。** 向きの検知は UI 層の責務
5. **リプレイ専用の分岐は 5 箇所のまま**

## 検証

| 種別 | 内容 |
|---|---|
| Vitest | `requestRepaginate()` が `waiting` 以外で無視されること。リプレイ中に無視されること。`consumed` を跨いだページ番号が単調であること |
| Vitest | 再測定後の `pageBreaks` が `measureFrom` を加味した絶対位置になること |
| Playwright | 縦長ビューポートで場面が 16:9、ステージがビューポート全体であること |
| Playwright | 縦長ビューポートで上下比が 50:50 であること |
| Playwright | 横長ビューポートでの寸法が現状と一致すること（回帰） |
| Playwright | 本文表示中に向きを変えるとページが割り直され、読んでいた位置が保たれること |

既存の `tests/e2e/read-through.spec.ts` の
「ステージは縦長でも横長でも 16:9 を保つ」は**この変更で必ず落ちる。**
「横持ちはステージ、縦持ちは場面が 16:9」に書き替える。

## 残る制約

- **背景の左右が最大 49% 切れる。** 作品側が「中央に重要なものを置く」配慮をすれば緩和されるが、
  エンジンは強制しない
- **URL バーの伸縮では再測定しない。** 向きの変化だけを見るため、
  バーの出入りで枠の高さが変わっても次のブロックまで反映されない
- **縦持ち専用の背景素材には対応しない。** 必要になったら別途設計する
