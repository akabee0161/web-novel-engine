# バックログと音声の設計

- 日付: 2026-08-07
- 状態: 確定

## この文書の位置づけ

[初期要件と保存設計](2026-08-07-initial-requirements-and-save-design.md) が
未確定として残した2件、**バックログ**と**モバイルブラウザの音声 autoplay 制限**に決定を与える。

この2件を技術スタックより先に決めたのは、どちらもエンジンのコア設計
（状態の持ち方、起動フロー）に影響しうるためで、
技術スタックを決めてから発覚すると手戻りになるからである。

なお、どちらも作品の質を左右する主題ではない。
実際に動かして不満が出た時点で見直す前提の決定であり、
ここでの目的は「後から変更すると高くつく部分だけを固定すること」にある。

## バックログ

### 決定

| 項目 | 決定 |
|---|---|
| 機能範囲 | 読み返しのみ。進行位置は動かさない（ジャンプしない） |
| 保持範囲 | 直近 N 件のリングバッファ。N の初期値は 200 |
| 単位 | 本文ブロック |
| 永続化 | しない。セッション限定 |
| 開けるタイミング | クリック待ちの瞬間だけ |

### データ構造

```js
backlog: [
  { speaker: "ミカ", body: "……帰ろうか" },
  { speaker: null,   body: "彼女は僕の袖を引いた。" },
]
```

既読ハッシュ `h` もセーブ連番 `i` も持たない。読み返しに必要ないため。

**この結果、バックログは既読の仕組みに一切影響しない。**
既読は従来どおりハッシュの Set のままでよく、
バックログはそれとは独立した表示履歴の配列として持つ。
検討前に懸念していた「既読ハッシュと本文ブロックの持ち方への影響」は、結論として無い。

### 積むタイミング

本文ブロックを表示した瞬間。既読の記録と同じ場所に並ぶ。

```js
readSet.add(step.h)
backlog.push({ speaker: step.speaker, body: step.body })
```

**シーン境界でクリアしない。** リングバッファは台本の構造と無関係に、
表示した順で 200 件を保つだけ。シーンをまたいで遡れる。

### 上限 200 の位置づけ

読者体験から導いた数ではなく、メモリ使用量の上限として置いた値。
平均 60 文字／ブロックとして約 25KB に収まる。

**調整可能な定数として1箇所に置く。** 実際に読んで足りなければ増やす。

### ロード復元時のリプレイ

特別扱いしない。

リプレイは既存設計どおり「演出の待ち時間をゼロにした通常再生」なので、
通過した本文ブロックはそのままバックログに積まれる。
結果として、ロード直後のバックログには現在シーンの先頭からの分が入っている。

読者にとって自然（ロードした地点の直前が読める）であり、
かつリプレイ処理に条件分岐を持ち込まずに済む。

### バックログはスナップショットに含めない

これは設計上の不変条件4「シーン境界で持ち越される状態は、すべてスナップショットに含める」の
**明示的な例外**である。理由は2つ。

1. バックログは画面の見た目を決める演出状態ではなく、単なる表示履歴。
   含めなくても復元後の画面は完全に一致する。
2. 上記のとおり、リプレイが自動的に埋める。

### 開けるのはクリック待ちの瞬間だけ

**セーブ可能点とまったく同じ条件にする。**

- 文字送り中に開こうとしたら、文字送りを完了させてから開く
- 演出中（フェード・トランジション・`@wait`）は開かない

これにより「バックログを開いている間に演出が進む」という問題が丸ごと消える。
セーブ可能点の限定と同じ考え方で、解かずに仕様から取り除く。

### 却下した案

| 案 | 却下理由 |
|---|---|
| 読み返し＋ジャンプ（その位置から読み直す） | セーブ復元と同じ「シーン入口からのリプレイ」が必要になり、コア設計に踏み込む。読み返しの needs に対して代償が大きい |
| セッションをまたいで作品全体を保持 | 本文全文をストレージに持つことになり、localStorage を圧迫する |
| 上限を文字数で決める | メモリは直接押さえられるが、遡れる量が場面によって変わる |
| 上限をシーン数で決める | 読者には自然だが、シーン長が台本次第なのでメモリ上限が確定しない |

## 音声と開始フロー

### 前提となる制約

| 制約 | 内容 |
|---|---|
| autoplay 制限 | `AudioContext` は `suspended` 状態で生成され、ユーザージェスチャ内で `resume()` するまで音が出ない |
| ジェスチャの資格 | `await` を挟むとジェスチャ扱いが切れる。unlock は同期的に行う必要がある |
| iOS の音量制御 | iOS Safari は `HTMLMediaElement.volume` への代入を無視する |
| サイレントスイッチ | iOS でマナーモードが ON のとき、Web Audio の音は鳴らない |

### 開始フロー

```
URL を開く
  └→ タイトル画面（@title の文字列 ／「はじめから」「つづきから」）
       └→ ボタン押下 ＝ ユーザージェスチャ
            ├─ AudioContext を生成して resume()、無音バッファを1回鳴らして unlock
            └─ 本編開始（以降 @bgm / @se は自由に鳴る）
```

タイトル画面を必ず挟む。セーブスロットの入口としてどのみち必要であり、
音声の unlock 点を兼ねさせれば、本編開始時点で既に音が鳴る状態になる。

**実装順序が制約される。** unlock はジェスチャのコールバック内で同期的に行うため、
「素材のロードを待ってから resume」ではなく「resume してから素材をロード」の順になる。

### 再生方式は Web Audio API に統一する

`<audio>` 要素は使わない。

決め手は iOS Safari が `HTMLMediaElement.volume` を無視することで、
これでは `@bgm stop fade:800` が実装できない。
Web Audio の GainNode なら `linearRampToValueAtTime` で確実にフェードできる。

```
BGM (AudioBufferSourceNode, loop) → GainNode(bgm) ┐
SE  (AudioBufferSourceNode)       → GainNode(se)  ┼→ GainNode(master) → destination
```

システムデータに持つ音量設定が、そのまま各 GainNode に対応する。

### バックグラウンド復帰

タブ切替や画面ロックで `AudioContext` は `suspended` に落ちる。二段構えで戻す。

1. `visibilitychange` で visible になったら `ctx.resume()` を試みる
2. それでも `suspended` なら、次のクリックで `resume()` する
   （ADV なのでクリックは必ず来る）

`resume()` は冪等なので、両方走っても害はない。

### `@bgm` の意味論

| 状況 | 挙動 |
|---|---|
| 現在と同じ名前の `@bgm` が再度来た | **鳴らし直さない。** 曲頭に戻さず、そのまま再生を継続する |
| 別の名前の `@bgm` が来た | 差し替える |
| ロード復元 | スナップショットの `bgm` を曲頭から鳴らす |

同名再指定で鳴らし直すと、BGM がシーンをまたいで持ち越される既存設計と噛み合わない。
シーンを細かく切るコストをゼロにする方針が壊れる。

**曲の再生位置はセーブしない。** スナップショットが「静止した画面」でなくなるため。

`@se` は逆に、同名でも毎回鳴らす。効果音は状態ではなく発火であり、
重なって鳴ってよい。したがってスナップショットの対象にもならない。

### 素材の先読み

プリロード全体の設計は別項目（未着手）だが、音声には固有の事情がある。

`decodeAudioData` は非同期で、BGM 1曲あたり数百ms〜数秒かかる。
**タイトル画面の滞在時間が、そのまま先読みの窓になる。**

実装の詳細は技術スタック確定後に詰める。
ここでは「タイトル画面には先読みの窓という役割もある」ことだけ記録しておく。

### サイレントスイッチには対応しない

iOS でマナーモードが ON のとき音は鳴らない。これを仕様として受け入れる。

OS の設定は読者の意思表示であり、エンジンが覆すべきものではない。

### 却下した案

| 案 | 却下理由 |
|---|---|
| タイトル画面を作らず即本編、音は最初のクリックから | 冒頭が無音になる。セーブのロード入口も別途必要になり、結局なにか画面が要る |
| 「タップして開始」オーバーレイのみ | 実装は最小だが、ロードの入口が残る |
| 無音 `<video>` ハックでマナーモードを迂回 | iOS のバージョンごとに壊れやすく、電池も食う。読者の設定を覆す点も正当化しづらい |
| 無音を検知して読者に告知 | サイレントスイッチの状態を読む API が無く、Web Audio は再生成功を返す。確実な検知手段が存在しないため、誤検知でノイズになる |

## この決定が後段に与える制約

| 制約 | 影響先 |
|---|---|
| タイトル画面が必須 | 起動フロー、ルーティング、素材の先読みタイミング |
| Web Audio API を使う | 技術スタック選定。音声ライブラリを選ぶ場合も GainNode 相当のフェードが要件 |
| バックログはスナップショット対象外 | 不変条件4 の例外として、命令追加時の判断表に載せる |
