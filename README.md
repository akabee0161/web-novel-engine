# web-novel-engine

ブラウザで動作するサウンドノベル / ビジュアルノベルエンジン。

自分が書くノベルを載せるための道具であり、想定利用者は自分ひとり。

## 目標

1. **自分の台本が実際に必要とした機能だけを作る。**
   機能の要否を決めるのは既存エンジンの機能表ではなく、自分が書いた台本。
   台本に出てこない機能は作らない。
2. **エンジンの命名はサイトブランドから独立させる。**

## 現状

**設計段階。実装コードはまだない。**

機能一覧から設計を起こすのではなく、先に台本を書き、そこから必要な命令セットを
確定させる方針を取っている。現在は台本の叩き台から命令を抽出し終え、
セーブ・既読・バックログ・音声まで仕様が固まったところ。次は技術スタックの決定。

### 技術スタック検討の最優先事項

**エンジンと作品コンテンツの境界をどこに引くか**から決める。
このエンジンで複数の作品を作ることを前提とするため、リポジトリとビルドの構成が
これに従属する。取りうる形は3つ。

| 形 | ビルド構成への影響 |
|---|---|
| 作品ごとに別サイト。エンジンはライブラリとして配布 | ライブラリとしてビルドする。エンジン側に公開APIの設計が要る |
| 1サイトに複数作品を載せ、作品選択画面を持つ | 単一アプリ＋ルーティング。起動フローがタイトル画面の前に1階層増える |
| 1リポジトリに作品を同居させ、作品ごとにビルド出力を分ける | モノレポ構成の要否が決まる |

後から変えるとビルド構成の作り直しになるため、フレームワークやビルドツールを
選ぶ前にここを決める。

一方、**作品選択画面・作品一覧UI・作品横断のセーブ管理は今は決めない。**
2作目が存在してから決めればよく、目標1（台本に出てこない機能は作らない）にも反する。

方向性自体は既存の決定に埋まっている。ストレージキーが `wn:<作品ID>:save:1` の形で
同一オリジンに複数作品が共存できる前提になっており、目標2 もエンジンを
特定作品から切り離す意図の表明である。未決なのは物理的な分け方だけ。

## 台本の第一原則

無記号のプレーンテキストが、そのままで最小の台本として成立すること。
記法なしの原稿がパースエラーになってはならず、演出はすべて後付けの差分である。

```
── 執筆直後（このまま動く） ──
「おつかれ。刷り上がったよ」

部長は束の一番上を持ち上げた。


── 演出と話者を足した後 ──
@bg clubroom_day fade:600
@bgm daily

>ミカ
「おつかれ。刷り上がったよ」

部長は束の一番上を持ち上げた。
```

詳細は [スクリプト構文リファレンス](docs/script-syntax.md) を参照。
